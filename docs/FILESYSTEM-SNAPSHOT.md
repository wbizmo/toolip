# Filesystem input consistency

Toolip discovers project files without following symbolic links. A symbolic directory makes discovery incomplete because its children cannot be represented safely in the current traversal. A symbolic file is retained as an input candidate but its reader rejects an outside-root target or a final-component symlink. Discovery errors fail the scan rather than silently removing paths from the input set.

Text reads enforce per-file, aggregate-byte and file-count budgets before allocating output buffers. The reader uses a zero-initialized buffer, loops over short reads, and checks for early EOF and growth past the observed file length. It compares device, inode, size, modification time and change time from discovery and from the open descriptor, then rechecks path identity and canonical containment after reading. A changed or cancelled read returns no content and releases its reserved byte budget. Successful reads include a SHA-256 of the exact bytes returned to analyzers and the checked descriptor snapshot. Findings from filesystem-backed analyzers carry JSON-safe source provenance: relative path, byte count, SHA-256, discovery snapshot, and verified read snapshot. Device and inode identifiers are serialized as decimal strings, so reports remain valid JSON. Findings from content providers carry the digest of the supplied content and discovery metadata when available; they do not claim descriptor metadata for provider-supplied bytes.

Source files use the default 2 MiB per-file budget. Project profiling reads the root `package.json` with a separate 16 MiB cap and one-file aggregate budget, preserving support for large manifests without making content scans unbounded.

For `F` discovered paths, `B` bytes read and `N` findings, discovery and identity checks are O(F) metadata operations; sorting remains O(F log F). Reading and hashing is O(B) time and O(T) additional memory across concurrent reads, where `T` is the configured aggregate-byte budget; each individual buffer is bounded by the per-file limit. Provenance adds O(N) references to per-file metadata, or O(F) metadata objects, without building a separate project-wide source copy.

The implementation reduces path races by comparing canonical paths and opened-file identity before and after each read. Portable Node.js APIs do not provide an equivalent race-free `openat`/directory-handle traversal on every supported OS; descriptor reads and post-read identity checks are therefore part of the guarantee, and concurrent mutation that is detected is reported as incomplete. These checks do not make arbitrary concurrent filesystem mutation impossible on every filesystem.
