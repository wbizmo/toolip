# Toolip v3.2.1 — Batch Implementation and Release Route

> Status: **plan, not delivered**. Maintained under [master epic #88](https://github.com/wbizmo/toolip/issues/88). Baseline: Toolip v2.2.1. Target: one final, authorized v3.2.1 release. This plan covers 65 original issues plus CI governance #93 and the P0 repository-compromise requirements #95 and #96: **68 implementation issues**.

## Binding delivery contract

1. **One batch, one branch, one PR.** Implement one batch at a time against current `main`. Push the batch branch and open its PR; do not publish npm or make a GitHub release.
2. **No premature issue closure.** Add `Closes #N` for each fully resolved issue in the PR description; the issues close only after GitHub merges the PR into the default branch. If an issue is partially addressed, use `Refs #N`, not `Closes`.
3. **No auto-release on merge.** `publish.yml` and `github-release.yml` must be manual-only; release operations require the exact version, explicit authorization, a verified tag and `main` alignment. The `npm-release` environment needs required reviewers set in repository settings.
4. **Every PR must pass** TypeScript typecheck, compiler-backed quality checks, build, tests, dependency audit, changed-file lint/format, secret detection, CodeQL and the existing cross-platform CI matrix. Failed or unknown checks block merge; do not weaken checks or suppress findings to get a green result.
5. **Versioning:** keep public documentation and `package.json` truthful for the current v2.2.1 release during implementation. Only Batch 19 updates both package manifests to v3.2.1, creates new versioned release notes and prepares final publication.
6. **Release authorization is separate from PR merge.** No `npm publish`, GitHub release, release tag or versioned npm artifact until all workstream acceptance criteria pass and the owner explicitly approves the final release.
7. **Security:** use least-privilege Actions permissions, no publish credentials in PR jobs, pinned third-party Actions, no `pull_request_target`, no execution of untrusted package scripts solely for inspection, explicit failure and bounded work. **#96 requires verified trusted Stage A scanning before any untrusted repository install/build scripts in Stage B.**
8. **Algorithm discipline:** report worst-case time and peak space Big-O, measured complexity-sensitive baselines, and any changed data structures in each PR. Prefer `O(V + E)` graph walks and `O(n)` indexed joins over nested `O(n²)` scans. See `docs/ENGINEERING.md` and the PR template. A review must reject unexplained asymptotic regressions.

## Repository-compromise P0 gates — new #95 and #96

**Batch 11 (#95):** Recognize executable code despite unrelated extensions, shebang-only/extensionless names and encoded loader content. Statistically inspect root scripts, `eslint.config.js`, `.vscode/tasks.json` (`runOn: folderOpen`), hooks and CI commands, then build a bounded cross-file execution-chain graph. Detection never executes input. Require harmless synthetic positive/negative fixtures, redacted evidence, confidence labels and explicit skipped/unknown coverage.

**Batch 16 (#96):** Establish a separately verified, immutable scanner/bootstrap on inert PR checkout _before_ executing any project-controlled scripts or npm lifecycle hooks. Inspect exact Git blobs and reachable referenced content. Require a fail-closed result on missing scanner, unknown/unsafe chain, timeout or provider failures according to approved policy. Test fork PR least privilege and dependency digest/provenance handling; do not pretend a valid signature guarantees benign behavior. Provide GitHub ruleset/branch-protection guidance as external repository settings.

**Early Batch 00 responsibilities:** enforce manual-only release workflows and document the pre-execution scanning order; avoid claiming the future Stage A detector is already available. Do not bypass failing quality/security checks.

**Algorithms:** name file count F, scanned bytes B, graph vertices V and edges E; benchmark indexed near-O(F+B+V+E) discovery/graph passes where feasible, bound parser/encoding/archive expansion, and measure space/CPU on representative 1k/10k/50k-file fixtures.

**Limitations:** Toolip does not itself guarantee stopping an already-triggered local IDE task or authenticated adversary push to an unprotected branch. Pair it with GitHub rulesets and reviews.

## Acceptance matrix for every batch

- Design and threat model: link issues, exact acceptance criteria, interface/API compatibility and security trust boundaries.
- Correctness: deterministic behavior, clean/failed/partial status separation, rollback tests, adversarial/regression fixtures.
- Algorithmic analysis: define input dimensions, state before/after worst-case time complexity and peak space complexity, justify new indexes/caches and bounded concurrency; provide measured comparisons where meaningful.
- Performance tests: comparable data sizes, locked fixtures, warm/cold measurements where applicable, no unexplained memory or CPU regressions. Use baseline-relative budgets before setting absolute 50k-file limits.
- CI: `npm ci`, `npm run typecheck`, `npm run quality`, `npm run build`, `npm test`, `npm run audit:runtime`, PR style/security jobs and existing `npm run verify` matrix.
- Completion: PR approved and merged into `main`, linked issues closed automatically, epic checklist updated, no npm publish side effect.

## Final release gate

After Batch 19 merges, confirm all **68** implementation issues (including #95/#96) are merged and closed, tests and full OS/Node matrix green, security findings triaged, packed tarball install/smoke tests and provenance verified, all documentation truthful, and npm trusted-publisher configuration reviewed. Then **manually** create the final GitHub release from `main`; verify `v3.2.1` matches the exact `main` commit; separately **manually** authorize npm publication. A merged PR is never itself a release.

> Important: CodeQL upload surfaces findings but does not itself guarantee that security alerts block a merge. Enable Code Scanning/required checks and configure repository rulesets/branch protection separately. These settings cannot be enforced merely by adding Markdown or YAML.
